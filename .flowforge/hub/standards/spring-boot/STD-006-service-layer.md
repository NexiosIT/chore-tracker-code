# Service Layer Pattern

> Backend services MUST implement transactional domain logic with application-assigned identifiers, consistent monetary precision, N+1-safe data access, and error handling that prevents domain errors from leaking to the caller.

## Motivation

Without a consistent service layer pattern, generated code scatters business logic unpredictably. Monetary calculations use inconsistent precision. N+1 query problems emerge. Error handling is ad-hoc. A standard service layer pattern ensures domain logic is centralized, performant, and predictable across all features.

## Rules

1. Every service class MUST implement business logic in methods marked `@Transactional`. Read-only queries MUST use `@Transactional(readOnly=true)`. Write operations MUST use `@Transactional` without the `readOnly` flag (defaults to `false`).

2. Service methods that throw errors MUST throw `DomainException` (or domain-specific subclasses) with an `error_code` in UPPER_SNAKE_CASE. Errors MUST NEVER be caught within the service; they propagate to the controller layer for translation to HTTP responses.

3. Entity lookups MUST use `Optional.orElseThrow()` with a `DomainException` that includes the entity type and ID:
   ```java
   User user = userRepository.findById(userId)
     .orElseThrow(() -> new DomainException("NOT_FOUND_USER", "User not found"));
   ```

4. New entities MUST be assigned their identifier immediately upon creation in application code (e.g. `UUID.randomUUID()` for the default UUID id — see STD-008 Rule 1). Identifiers MUST NOT be generated by the database.

5. Timestamp fields (`createdAt`, `updatedAt`) MUST be set to `LocalDateTime.now()` at creation/update time. The database MUST NOT set these values.

6. For batch lookups that prevent N+1 queries, use `findByIdIn(Collection<UUID> ids)` and then iterate the result in application code rather than querying in a loop.

7. Monetary values (currency amounts, balances) MUST use `BigDecimal` with `setScale(2, RoundingMode.HALF_UP)` for all arithmetic operations to ensure correct rounding to cents. Precision MUST be enforced at the service layer, not deferred to the database.

8. Response objects MUST be built in private helper methods, not inline in the public method. This separates transformation logic from business logic and makes testing easier.

9. **No insert-then-fetch within the same transaction.** A service method MUST NOT insert (or save) an entity and then query the repository for that same entity within the same `@Transactional` boundary. The in-memory object returned by `repository.save()` is the authoritative reference — use it directly. Re-fetching a just-inserted row creates unnecessary database round-trips, risks read-consistency issues across isolation levels, and masks bugs where the persisted state diverges from the in-memory state.

## Examples

### Compliant: Service method with error handling

```java
@Service
@RequiredArgsConstructor
public class AccountService {
  private final AccountRepository accountRepository;
  private final TransactionRepository transactionRepository;

  @Transactional
  public AccountResponse withdraw(UUID accountId, BigDecimal amount) {
    Account account = accountRepository.findById(accountId)
      .orElseThrow(() -> new DomainException(
        "NOT_FOUND_ACCOUNT",
        "Account not found"
      ));

    BigDecimal scaledAmount = amount.setScale(2, RoundingMode.HALF_UP);
    if (account.getBalance().compareTo(scaledAmount) < 0) {
      throw new DomainException(
        "BUSINESS_INSUFFICIENT_BALANCE",
        "Insufficient balance for withdrawal"
      );
    }

    account.setBalance(account.getBalance().subtract(scaledAmount));
    account.setUpdatedAt(LocalDateTime.now());
    accountRepository.save(account);

    Transaction txn = new Transaction();
    txn.setId(UUID.randomUUID());
    txn.setAccountId(accountId);
    txn.setAmount(scaledAmount);
    txn.setType("WITHDRAWAL");
    txn.setCreatedAt(LocalDateTime.now());
    txn.setUpdatedAt(LocalDateTime.now());
    transactionRepository.save(txn);

    return buildAccountResponse(account);
  }

  @Transactional(readOnly = true)
  public List<AccountResponse> listAccounts() {
    // Batch load for N+1 prevention
    List<Account> accounts = accountRepository.findAll();
    return accounts.stream()
      .map(this::buildAccountResponse)
      .collect(Collectors.toList());
  }

  private AccountResponse buildAccountResponse(Account account) {
    return AccountResponse.builder()
      .id(account.getId())
      .balance(account.getBalance())
      .updatedAt(account.getUpdatedAt())
      .build();
  }
}
```

### Compliant: Batch loading to prevent N+1

```java
@Transactional(readOnly = true)
public List<OrderResponse> getOrdersWithItems(List<UUID> orderIds) {
  // Single query for orders
  List<Order> orders = orderRepository.findByIdIn(orderIds);

  // Single query for all items (batch)
  List<UUID> ids = orders.stream().map(Order::getId).collect(Collectors.toList());
  List<OrderItem> items = orderItemRepository.findByOrderIdIn(ids);

  // Map items back to orders in memory (no N queries)
  Map<UUID, List<OrderItem>> itemsByOrderId = items.stream()
    .collect(Collectors.groupingBy(OrderItem::getOrderId));

  return orders.stream()
    .map(order -> buildOrderResponse(order, itemsByOrderId.getOrDefault(order.getId(), emptyList())))
    .collect(Collectors.toList());
}
```

### Compliant: Identifier generation

```java
@Transactional
public ProductResponse createProduct(CreateProductRequest req) {
  Product product = new Product();
  product.setId(UUID.randomUUID());          // id generated here, not by DB
  product.setName(req.getName());
  product.setPrice(req.getPrice().setScale(2, RoundingMode.HALF_UP));
  product.setCreatedAt(LocalDateTime.now());
  product.setUpdatedAt(LocalDateTime.now());

  productRepository.save(product);
  return buildProductResponse(product);
}
```

### Compliant: Using the saved entity directly (Rule 9)

```java
@Transactional
public OrderResponse createOrder(CreateOrderRequest req) {
  Order order = new Order();
  order.setId(UUID.randomUUID());
  order.setStatus(OrderStatus.PENDING);
  order.setCreatedAt(LocalDateTime.now());
  order.setUpdatedAt(LocalDateTime.now());

  Order saved = orderRepository.save(order);
  // Use 'saved' directly — do NOT re-fetch from the database
  return buildOrderResponse(saved);
}
```

### Non-Compliant: Insert then re-fetch in the same transaction (Rule 9)

```java
// BAD: Saves entity then immediately queries for it — unnecessary round-trip
@Transactional
public OrderResponse createOrder(CreateOrderRequest req) {
  Order order = new Order();
  order.setId(UUID.randomUUID());
  order.setStatus(OrderStatus.PENDING);
  order.setCreatedAt(LocalDateTime.now());
  order.setUpdatedAt(LocalDateTime.now());

  orderRepository.save(order);

  // BAD: Re-fetching the same entity we just inserted
  Order fetched = orderRepository.findById(order.getId())
    .orElseThrow();
  return buildOrderResponse(fetched);
}
```

### Non-Compliant: Exception caught and silently swallowed

```java
// BAD: Error caught and ignored
@Transactional
public void sendNotification(UUID userId, String message) {
  try {
    notificationService.send(userId, message);
  } catch (Exception e) {
    // Silently swallows the error — caller never knows it failed
  }
}
```

### Non-Compliant: BigDecimal without scaling

```java
// BAD: No rounding — introduces precision errors
@Transactional
public void applyInterest(UUID accountId, BigDecimal rate) {
  Account account = accountRepository.findById(accountId)
    .orElseThrow();
  account.setBalance(account.getBalance().multiply(rate));  // No scaling — wrong
  accountRepository.save(account);
}
```

### Non-Compliant: Inline response building

```java
// BAD: Response built inline, mixing transformation with logic
@Transactional
public Map<String, Object> getOrderData(UUID orderId) {
  Order order = orderRepository.findById(orderId)
    .orElseThrow();

  return Map.of(
    "id", order.getId(),
    "status", order.getStatus(),
    "items", calculateTotalItems(order),  // mixed into return
    "total", order.getTotal()
  );
}
```

## Applicability

- **Service types:** backend services with business logic
- **Domains:** all
- **Exceptions:** None. All business logic layers follow this pattern.
